# Feature Specification: iOS 真机 system scope

**Workspace**: `ios-system-scope`
**Created**: 2026-08-11
**Status**: Draft
**Input**: 用户描述: "iOS 真机 system scope：用 out-of-process XCUITest runner 补齐 Reticle 进程内够不到的系统层能力（另一进程的树、显示级截图、跨进程坐标手势）"

---

## 背景与定界

Reticle 在 iOS 真机上的一切观察和驱动都发生在**目标 app 进程内部**（linked agent）。这带来一条结构性盲区，`docs/boundaries.md` 的 "Real-device iOS input" 与 "Out-of-process system UI" 两行已经承认了它：系统权限弹窗、输入法自己的窗口、SpringBoard、Home / 应用切换手势，既不在这个 app 的任何窗口里，也不在它的任何节点里，连进程内截图也拍不到。目前 Reticle 对这类目标的回答只能是「按名拒绝并说明」。

本需求引入**第二条通道**：一个独立于目标 app 的常驻进程（下称 runner），它在系统层拥有目标 app 没有的观察和输入权限。已在 iPhone 13 Pro Max / iOS 26.0 上实证该通道成立，包括系统弹窗的读取与点击、把 app 踢到后台、SpringBoard 树读取、跨进程坐标手势，以及显示级截图。

下文「系统层界面」一律指：**当前显示在屏幕上、但不属于目标 app 的界面**——系统弹窗、主屏、输入法自己的窗口、应用切换器。目标 app 自身的界面不在此列，读它仍应走现有的 app 内通道。

「最上层覆盖物」指：**当前压在目标 app 之上、不属于目标 app 的那一个界面**。系统弹窗是最典型的一个。当目标 app 自己就在最前面时，不存在最上层覆盖物。

system 通道的就绪程度分**两个状态**，因为两者失败后要做的事完全不同：

- **已安装** — 准备工作（构建、签名、装机）已完成。不满足时需重新准备。
- **已连通** — runner 进程存活且能应答。不满足时只需重新启动它，无需重新准备。

**这条通道不是原有能力的增强，是另一种来源。** 它能看到的东西更少（只有无障碍一层，没有 view 层、Compose 语义、WebView DOM、样式、区域），但能看到进程内看不到的地方。因此它必须以独立命令、独立证据来源出现，不能与现有 `ui` / `act` 的输出合流——否则「这条通道读不到」会被读成「app 真的没有」。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 把设备准备成可用状态，并能收摊 (Priority: P1)

作为在真机上做验证的使用者，我希望用一条命令把 system 通道所需的设备准备工作做完、并能在用完后显式收掉常驻进程，且在任何一步不满足时得到指名道姓的原因，以便我不必靠猜测和反复试错去凑齐前置条件，也不必担心设备上留下我不知情的东西。

**Why this priority**: 这条通道的前置条件多且失败会伪装成别的错误（实测：设备端开关没开时，先表现为一个与它无关的连接错误，清干净重装后才报出真实原因）。准备阶段说不清楚，后面所有能力都用不上。

**Acceptance Scenarios**:

1. **[US1-1]**
   **Given** 一台已连接、已开启开发者模式、已开启系统 UI 自动化开关的真机
   **And** 使用者提供了一个在本机可用的签名团队标识
   **When** 使用者执行准备命令
   **Then** 命令完成后报告 runner 已达到「已安装」状态，并给出可复用的设备标识
   **And** 后续会话不需要再次构建即可使用该 runner

2. **[US1-2]**
   **Given** 一台设备端「系统 UI 自动化」开关未开启的真机
   **When** 使用者执行准备命令
   **Then** 命令失败，并明确指出是设备端该开关未开启、需要在设备上手动开启，而不是报告为连接失败或超时

3. **[US1-3]**
   **Given** 使用者提供的签名团队在本机没有可用的签名材料
   **When** 使用者执行准备命令
   **Then** 命令失败，并说明是签名材料不可用，同时列出本机实际可用的团队标识供选择

4. **[US1-4]**
   **Given** 一台已有存活 runner 的真机
   **When** 使用者执行停止命令
   **Then** runner 退出，system 通道回到「已安装但未连通」状态
   **And** 目标 app 与设备当前前台状态不因这次停止而改变

**Edge Cases**:

- **[US1-5]** 设备已装有一个版本过旧的 runner 时，准备命令替换它而不是与之共存，并在结果中说明发生了替换
- **[US1-6]** 设备锁屏或熄屏时执行准备命令，命令说明设备需要处于解锁状态，而不是长时间挂起后超时
- **[US1-7]** 同一台设备上已有一个存活的 runner 时，重复执行准备命令不产生第二个存活实例
- **[US1-8]** 对一个本就没有存活 runner 的设备执行停止命令，命令成功并说明本无可停止的实例，而不是报错

### User Story 2 - 读取另一个进程的界面 (Priority: P1)

作为在真机上做验证的使用者，我希望能读到当前压在目标 app 之上的系统界面（权限弹窗、系统提示等）的结构与文字，以便在被它挡住时知道挡住我的到底是什么、上面有哪些可操作项。

**Why this priority**: 这是这条通道最主要的价值，也是现有能力唯一无法用任何方式绕过的盲区。

**Acceptance Scenarios**:

1. **[US2-1]**
   **Given** 目标 app 触发了一个系统权限弹窗，弹窗正压在 app 之上
   **When** 使用者请求读取系统层界面（不指定读取对象）
   **Then** 返回结果是**最上层覆盖物及其子树**，包含该弹窗的标题文字、说明文字和它的每一个可操作项，每项带自己的位置与可否被点中
   **And** 结果明确标注这些内容来自 system 通道，而非目标 app 自身

2. **[US2-2]**
   **Given** 当前没有任何系统界面压在目标 app 之上
   **When** 使用者请求读取系统层界面
   **Then** 返回结果说明当前系统层没有覆盖物，而不是返回一个空结果让使用者自行推断

3. **[US2-3]**
   **Given** 使用者需要读的不是最上层覆盖物，而是主屏或某个指定 app 的界面
   **When** 使用者显式指定读取对象
   **Then** 返回该对象的界面
   **And** 若该对象的节点数超出读取上限，结果被截断并说明截断了多少、上限是多少

4. **[US2-4]**
   **Given** 使用者已通过 system 通道读到一个界面
   **When** 使用者查看结果中每个节点的属性
   **Then** 该通道读不到的属性（如样式、区域划分、真实控件类名）以「此通道无法读取」的形式出现，而不是以空值出现

**Edge Cases**:

- **[US2-5]** 请求读取时系统界面刚好消失，结果说明界面已不在，而不是返回一份可能已过期的内容
- **[US2-6]** 读取耗时超过约定上限时，命令中止并说明是该通道的固有耗时特性所致，而不是无限期等待
- **[US2-7]** 读取过程中 runner 进程消失，该次读取自动重试一次；重试仍失败则报错，并说明 runner 曾中断过

### User Story 3 - 驱动另一个进程的界面 (Priority: P1)

作为在真机上做验证的使用者，我希望能点击系统弹窗上的按钮、把 app 送到后台、在系统界面上做坐标手势，以便让流程越过这些进程外的关卡继续走下去。

**Why this priority**: 只能看不能动的话，遇到系统弹窗的流程依然是断的；而权限弹窗几乎出现在所有真实流程的开头。

**Acceptance Scenarios**:

1. **[US3-1]**
   **Given** 一个系统权限弹窗正压在目标 app 之上
   **When** 使用者通过 system 通道点击弹窗上的某个可操作项
   **Then** 该项被真实点中，弹窗按其语义关闭
   **And** 结果记录本次动作经由 system 通道、作用于哪个进程

2. **[US3-2]**
   **Given** 目标 app 正在前台
   **When** 使用者通过 system 通道执行「回到主屏」
   **Then** 目标 app 离开前台，结果以 app 的实际状态变化作为证据，而不是仅报告指令已下发

3. **[US3-3]**
   **Given** 目标 app 因某次操作离开了前台
   **When** 使用者通过 system 通道让目标 app 重新回到前台
   **Then** 目标 app 回到前台且**不被重启**，其原有界面状态与进行中的流程得以保留

4. **[US3-4]**
   **Given** 使用者要点的目标在系统界面上，且只知道它的坐标
   **When** 使用者通过 system 通道在该坐标做手势
   **Then** 手势落在系统界面上，结果标明作用进程

**Edge Cases**:

- **[US3-5]** 指定的可操作项在系统界面上不存在时，命令失败并列出该界面上实际存在的可操作项，而不是静默无动作
- **[US3-6]** 指定坐标落在屏幕范围之外时，命令拒绝执行并说明坐标越界
- **[US3-7]** 动作下发后界面没有发生任何变化时，结果如实报告「已下发但未观察到变化」，不把「已下发」表述为「已生效」

### User Story 4 - 拿到包含进程外内容的画面 (Priority: P2)

作为在真机上做验证的使用者，我希望拿到一张包含系统弹窗在内的真实屏幕画面，以便在结构信息不足以说明问题时，用画面作为证据。

**Why this priority**: 现有的真机截图来自 app 进程内部，对进程外内容完全不可见——一张「看起来一切正常」的截图会误导判断。但它的价值低于能读能点，故次之。

**Acceptance Scenarios**:

1. **[US4-1]**
   **Given** 一个系统弹窗正压在目标 app 之上
   **When** 使用者通过 system 通道请求画面
   **Then** 得到的画面包含该弹窗
   **And** 结果标明该画面取自显示层，与 app 进程内截图的取景范围不同

2. **[US4-2]**
   **Given** 使用者同时拿到了进程内截图与 system 通道画面
   **When** 使用者比较两者
   **Then** 两者各自标明来源与取景范围，使用者能判断某项内容的缺失是「app 没画」还是「该通道拍不到」

**Edge Cases**:

- **[US4-3]** 设备熄屏时请求画面，结果说明屏幕未点亮，而不是返回一张纯黑图并让使用者误判为界面异常

### User Story 5 - 进程内够不到时得到准确指引 (Priority: P2)

作为在真机上做验证的使用者，当我的坐标动作打不到目标 app 的任何窗口时，我希望错误信息告诉我这既可能是坐标写错、也可能是目标在另一个进程，以便我选择正确的下一步而不是盲目重试。

**Why this priority**: 这是两条通道的交界处，也是最容易产生误判的地方。**明确不做自动改道**：坐标打不到本进程窗口时，最常见的原因是坐标本身就错了；自动改由 system 通道派发会把「坐标写错」变成「往另一个进程乱点」，比失败更糟。

**Acceptance Scenarios**:

1. **[US5-1]**
   **Given** 使用者在真机上对目标 app 做一个坐标动作，该坐标不在该 app 的任何窗口内
   **When** 动作执行
   **Then** 动作依然按名拒绝且不产生任何点击
   **And** 错误信息同时说明两种可能（坐标不正确 / 目标在另一进程），并指出后者应改用 system 通道

**Edge Cases**:

- **[US5-2]** system 通道当前不可用时，上述错误信息仍要说明这两种可能，同时区分它是「尚未安装」（需先准备）还是「已安装但未连通」（只需启动），并给出对应的下一步

## Non-Functional Requirements

- **NFR-001**: 会话开始时使用 system 通道，不得要求重新构建 runner。准备工作只在首次或 runner 变更时发生一次。
- **NFR-002**: system 通道的一切结果必须自带来源标识，使调用方在任何时候都能区分该信息来自 app 内通道还是 system 通道。
- **NFR-003**: 该通道读不到的属性必须以「无法读取」显式表达，不得以空值表达。理由：空值会被读成「app 真的没有」，与事实相反。
- **NFR-004**: 该通道不提供全界面遍历式的读取。已实测其逐属性读取的固有开销会使大范围遍历达到分钟级（实测一次含网页内容的遍历约两分钟），故读取必须是定向的、有节点数上限和耗时上限的。默认读取对象是最上层覆盖物；更大范围必须由调用方显式指定，且仍受上限约束。
- **NFR-010**: runner 常驻。一次准备之后它保持存活以跳过反复启动的开销，并提供显式停止命令供离场清理。「设备上有一个常驻进程」这一事实必须对使用者可见，不得隐式发生。
- **NFR-011**: runner 意外消失时，当次操作自动重启它并重试一次，且**必须在结果中说明发生过重启**——重启会打断设备当前的前台状态，对正在验证的流程是可观察的干扰，隐瞒它会让使用者把干扰误判为被测目标的行为。重试仍失败则报错，不再继续重启。
- **NFR-005**: 使目标 app 回到前台的操作不得重启它，以保持 Reticle「观察正在运行的 app」这一根本承诺。
- **NFR-006**: system 通道的任何失败都必须报告可执行的原因（缺少哪个设备端开关、缺少什么签名材料、runner 未就绪），不得暴露底层工具的原始报错。理由：实测底层报错会把「设备端开关未开」伪装成一个与之无关的连接错误。
- **NFR-007**: system 通道只出证据，不对界面是否「正确」下判断，与 Reticle 现有定位一致。
- **NFR-008**: 本能力仅适用于 iOS 真机。在模拟器上请求时应说明现有通道已覆盖该场景，并指出应使用哪条现有命令。
- **NFR-009**: 本能力新增的所有结构性不可达项必须登记到 `docs/boundaries.md` 的 Honest boundaries 表，与既有边界同一格式。

## Out of Scope

- 用 system 通道替代现有的 app 内观察通道。两者能力不同且不可互换，app 内通道仍是读取 app 自身界面的唯一完整来源。
- 通过 system 通道读取网页内容的结构与样式。已实测该通道只能读到无障碍层，网页自身的元素标识与样式完全不可见。
- 把 system 通道的节点并入现有界面报告的节点集合。
- Android 侧的对应能力。本需求由 iOS 真机的特有盲区驱动，Android 是否存在同一病因需另行实证后再定。
- 跨设备并行使用多个 runner。
- 对未安装、未签名或非开发者签名的第三方 app 使用本通道。
- 自动在进程内动作失败时改由 system 通道重试（已明确不做，理由见 US5）。
